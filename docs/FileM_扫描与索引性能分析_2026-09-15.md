# FileM 扫描与索引性能分析

日期：2026-09-15。以下保留优化前的分析和临时副本实验结论，源码行号对应分析时快照。后续已按此文档实施首批优化，当前行为、验收与对照测速见 [性能优化实施记录](FileM_性能优化实施记录_2026-09-15.md)。

## 判断

FileM 有可确认的额外开销。Windows 首次扫描优先优化逐文件句柄查询；持续扫描优先处理目录变化触发全量重扫；正文索引优先处理逐文件启动进程、固定等待和取任务查询。线程数需要按阶段、文件分布和存储设备测试，GPU 对这些路径没有直接帮助。

文件名/属性索引与正文索引是不同阶段。要与 Everything、AnyTXT 对比，必须对齐首次建库或增量更新、实际扫描范围、文件格式、排除规则及完成定义。

## Everything 与 AnyTXT 的可核实差异

Everything 首次建立 NTFS 索引可读取 MFT（卷内文件记录表），后续追踪 USN 变化日志。这减少了普通递归遍历的大量路径访问。名称、路径及配置启用的属性保存在索引中。网络盘和不支持快速路径的文件系统仍需要目录遍历。来源：[开发者说明](https://www.voidtools.com/forum/viewtopic.php?t=12371)、[索引文档](https://www.voidtools.com/support/everything/indexes/)、[文件夹索引](https://www.voidtools.com/support/everything/folder_indexing/)。

Everything 默认快速索引主要面向文件名及属性；1.5 另有可选正文索引，不能笼统说它完全不索引正文。来源：[官方 FAQ](https://www.voidtools.com/faq/)、[1.5 正文索引](https://voidtools.com/forum/viewtopic.php?t=9793)。

AnyTXT 官方可确认自带文档解析、持久全文索引及更新功能；未找到可确认其使用 MFT/USN、具体数据库或线程模型的官方材料。不能根据扫描快就推断其底层实现。来源：[官网](https://anytxt.net/)、[更新记录](https://anytxt.net/download/)。

FileM 当前 Everything 接口用于有搜索词时取得候选，并送入自己的索引校验流程；它不替代首次全量扫描。依据：`crates/filem-core/src/everything.rs:86-124`。

## 当前瓶颈与处理顺序

### 1. 先避免不必要的全量重扫

- 启动会对所有已保存范围刷新：`lib.rs:288-293`。
- 普通文件变化有增量处理，但新增/修改目录，或已删除的已知目录，可能让 `update_files` 返回 false，进而扫描整个监控范围：`scan.rs:945-972`、`scan_schedule.rs:267-288`。
- 8,192 个不同变更路径以上或监听事件丢失会升级全量：`watch.rs:19-34`、`lib.rs:565`。

忙碌的盘可能在扫描期间积累新请求，导致上一轮结束后又开始下一轮。这能够解释“文件数量不增加但一直扫描”的一种机制，尚不能确认是用户 Windows 上的实际原因。

建议：普通目录变更只核对受影响子树；合并父子请求；删除、重命名按已有索引处理；记录重扫来源与次数。Windows 持久保存 USN 游标，macOS 评估持久 FSEvents 游标，日志可用时追赶变化，丢失时再扩大核对范围。目录 mtime 不能证明整棵子树未变化。

验收：在十万目录树中新增一个子目录，不枚举其他无关子树；模拟事件丢失、重命名、取消及重启，验证无漏项、无无条件重复全扫。

### 2. Windows 批量读取目录项和文件身份

当前每个普通文件都额外执行 `CreateFileW → GetFileInformationByHandle → CloseHandle`：`scan.rs:221`、`platform.rs:124-145`。百万文件即百万次额外打开和查询；这在 Windows、小文件和高延迟路径上值得优先测量。Unix 身份来自已有 metadata 的 dev/ino，因此 Mac 测试不能验证这部分 Windows 收益。

优先评估支持返回文件 ID、大小和时间的批量目录枚举，减少逐文件打开。`FindFirstFileExW` 的大缓冲模式可减少往返，但它本身不提供当前所需的文件身份；需结合 `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` 等方案验证。来源：[FindFirstFileExW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfileexw)、[批量目录项结构](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_both_dir_info)。

进阶增加可选 NTFS 后端，使用文件记录枚举与变化日志。非 NTFS、网络路径及没有相应权限的用户使用普通后端。不能依赖管理员权限成为默认前提，也不能把 USN 记录时间当文件修改时间；USN 记录不含完整文件大小属性，额外属性读取也要计入成本。来源：[FSCTL_ENUM_USN_DATA](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_enum_usn_data)、[FSCTL_READ_USN_JOURNAL](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_read_usn_journal)、[USN_RECORD_V2](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-usn_record_v2)。

验收：记录每十万文件的句柄打开次数、枚举时间、属性查询时间，核对文件身份替换、硬链接、重解析点、云占位文件和范围权限。移动/删除前仍需重新验证文件身份。

### 3. 降低目录预统计和同步屏障的成本

当前严格目录比例使用两遍枚举：先遍历以建立目录清单，再重新遍历读取文件属性。预统计也会经过目录内所有文件项，只是跳过普通文件的完整属性和身份读取：`scan.rs:118-250,418-484`。

两遍各自还有目录 metadata/canonicalize 等校验。每次最多处理 64 个目录，等整组完成才开始下一组。一个慢目录会拖住整组；单个巨型目录内部仍是逐项处理，增加目录工作线程不能直接并行它。

建议：

- 保留用户要求的固定目录总数，评估首次枚举保存有界的临时文件清单，第二阶段处理清单，减少重新访问文件系统。此方案会增加临时写入，必须实测是否划算。
- 采用固定批次下的动态任务队列，目录完成即领取下一个，避免每 64 个目录的整组等待。
- 巨型目录可把昂贵的属性/身份工作按块交给受限工作池；读取、处理、写入使用有界队列。
- macOS 评估 `getattrlistbulk` 批量读取目录项和属性，随后结合 FSEvents 做增量；它仍需要遍历目录。来源：[Apple getattrlistbulk](https://github.com/apple/darwin-xnu/blob/main/bsd/man/man2/getattrlistbulk.2)、[FSEvents 使用指南](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html)。

验收：一个受控慢目录不得阻止其他快目录继续推进；分母固定、取消和文件操作暂停语义保持正确；记录内存和临时磁盘空间上限。

### 4. 数据库写入与界面统计

元数据按 512 文件提交，但每文件仍有查询、插入/更新及 memberships generation 更新。即使文件未变化，完整核对仍会更新成员的扫描代次：`scan.rs:731-901`。当前数据库为 WAL + synchronous=FULL：`db.rs:19`。

`summary` 每 1.2 秒轮询，revision 改变时重新计算文件数量、大小和分类聚合；正文状态也每 1.8 秒聚合。大库会出现反复全库统计，正文任务查询还占用主写入连接。

收尾还有特殊负载风险：旧扫描代次的条目逐项与失败路径列表匹配，约为“旧条目数 × 失败路径数”的工作量；每个 scope 又做一次全库孤儿清理：`scan.rs:663-682`、`db.rs:119-121`。权限失败很多、保留大量旧条目时应特别测量。

建议：批量预取已有记录、批量更新和按时间/数量提交；尽量减少未变化文件的写入；进度走轻量状态读取、数量/分类使用增量聚合或较低频独立刷新；失败路径建立前缀索引，清理限定本批受影响记录并合并 scope 收尾。保留操作记录的持久性保障，先测量提交等待再选择存储策略。

### 5. 正文索引有独立的高优先级瓶颈

仅在启用内容索引时涉及以下路径：

- 单个内容 worker；每个任务后固定等待 15 ms：`content.rs:141-164`。十万任务仅这一项就约 25 分钟，百万任务约 4.17 小时，这是代码计算的等待开销，不是完整实测时长。
- 每文件启动一个解析进程，并每 50 ms 查询退出状态：`extract.rs:362-405`。小文档实际解析很快时，进程启动和等待会占明显比例；50 ms 不是每个文件无条件固定下限，取决于首次检查时是否已经结束。
- 每次只从多表查询取一件任务，按扩展名候选及 id/depth 排序：`content.rs:170-173`。同 schema 的 EXPLAIN 检查发现扩展名扫描和临时排序，存在反复扫描大量候选的风险；需要在应用使用的 SQLite 上记录查询计划与耗时，不能仅凭 SQL 文本断言所有输入均为二次复杂度。
- 每个解析结果独立事务提交，触发 FTS 写入。

建议：常驻且有并发上限的解析进程池，保留每任务超时、内存限制和取消能力；批量领取任务或显式待处理队列；完成即领取下一件，使用事件唤醒；批量写入 FTS。TXT/代码与复杂 Office/PDF 分队列，以实测吞吐和内存占用调整并发。

验收：分别以小 TXT、DOCX/XLSX、文本 PDF 测量每秒文件数与 MB/s；检查索引结果一致、解析失败有终态、任务不反复领取。不能把文件名扫描完成当正文索引完成。

## 本轮临时副本测试

Release 构建；每种目录分布 3 万个 19 字节小文件；正文与监听关闭；1/4/8 个目录读取线程；每个设置一次新库扫描及两次无变化刷新。表中是后台两次刷新平均值，不含 200 ms 请求等待和前端轮询。

| 文件分布 | 1 线程 | 4 线程 | 8 线程 |
|---|---:|---:|---:|
| 全部文件集中在一个目录（含根共 2 目录） | 0.773 s | 0.629 s | 0.598 s |
| 分布在 100 个目录（含根共 101 目录） | 0.701 s | 0.642 s | 0.664 s |
| 分布在 10,000 个目录（含根共 10,001 目录） | 2.632 s | 1.366 s | 2.516 s |

4 线程、1 万目录样本：预统计平均约 0.377 s，读取/写入流水线约 0.923 s，收尾约 0.067 s。预统计约占本轮后台用时的 28%，不是零成本。平铺样本的写入调用耗时与流水线整体时长接近，增加读取线程的空间有限。

限制：macOS 本地合成暖缓存、固定顺序、每设置仅两次刷新；系统负载未隔离，分析期间另有数据库实验。8 线程样本波动很大，不能据此认定 8 线程一般都慢。表中数值不能作为 Windows、冷缓存、机械盘、网络盘或与 Everything/AnyTXT 的速度对比。`write_ms` 包含锁和提交等待，与读取并行，不能当 CPU 用时或与流水线时间相加。

原始阶段数据、源码校验值和方法：[scan-profile-20260915.json](benchmarks/scan-profile-20260915.json)。

## 实施建议

1. 先补轻量分阶段计时与重扫次数，修复目录变更扩大为全量扫描，改善持续扫描和重复启动。
2. Windows 批量属性/身份枚举，同时优化数据库批量写入与状态统计；保留跨平台普通扫描路径。
3. 启用正文索引的场景并行推进常驻解析池、批领任务、批量 FTS 提交。
4. 动态目录任务队列与巨型目录分块，再提供“自动/低占用/高性能”及高级并发设置，以 HDD、SSD、网络盘测试定默认值。
5. 对 Windows 大规模本地 NTFS 加可选日志驱动快速后端；macOS 使用对应的批量属性和事件机制。

GPU 不负责目录系统调用和 SQLite 提交，对以上瓶颈缺少直接收益。未来若支持 OCR、向量提取等计算密集任务，再单独评估 GPU。
