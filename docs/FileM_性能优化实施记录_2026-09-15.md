# FileM 性能优化实施记录

日期：2026-09-15。依据 [扫描与索引性能分析](FileM_扫描与索引性能分析_2026-09-15.md) 实施。当前为工作区改动，尚未发布新安装包。

## 已实现

### 普通目录事件限定到受影响子树

新增、删除和重命名子目录不再直接升级为整个监控范围重扫。父子事件合并后，只对最小受影响子树建立目录清单、核对文件并清理旧成员关系。其他子树的扫描代次保持不变。文件变成目录、目录变成文件也会清理原来的记录。

根目录事件、监听溢出/事件丢失、无法安全处理的增量事件仍触发完整核对。保留根目录身份、配置版本、排除规则、重解析点/符号链接检查；无法读取的路径保留旧索引并标记未完成。原有未完成警告不会被一次局部成功扫描清除。

### Windows 批量目录读取

新增 `scan_entry.rs`：优先通过 `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)`，每个目录使用 64 KiB 缓冲批量取得名称、大小、时间、属性和文件 ID。普通文件无需再为取得身份逐个打开句柄。

文件系统不支持该枚举方式时回退到普通遍历；文件 ID 不可用、重解析项等情况保留必要的单项校验。读取中途失败标记对应目录未完成，不混入重复遍历。文件移动、删除和正文提取之前仍重新验证当前文件身份。

这仍是目录遍历后端，不是 Everything 的 MFT/USN 建库方式。Windows 目标已通过编译检查，实际 NTFS/网络盘/云占位文件性能及行为待 Windows 机器验收。

### 动态目录调度和批量提交

保留“先统计目录总数，再按固定目录清单计算比例”。文件扫描阶段把整份固定清单交给有界工作池，线程完成一个目录后可继续处理其他目录，不再等待每 64 个目录整组结束。

读取结果通过有界队列交给写入线程，累计约 2,048 个文件或 64 个完成目录提交一次。目录完成数只在相关文件写入后推进。暂停执行文件操作后重读观察结果，防止旧路径写回索引。

旧成员关系与孤儿记录会在每个 scope 切换为已完成前同事务清理，避免界面读到“已完成但旧条目尚未删除”的短暂状态；批次末尾仍保留一次兜底清理。失败路径匹配改为祖先集合查询，避免每个旧文件逐一比较所有失败路径。继续保留 SQLite 的持久性设置。

### 正文解析与索引

使用有上限的解析工作池。每个工作线程复用独立解析进程，成功处理 64 份文档后回收；出错、取消、超时后丢弃进程。每任务保留 30 秒时限、内存限制和前后身份检查，结果通过带长度上限的帧协议传递，收到回复立即继续。

从专用只读连接按 ID 批量领取最多 128 项任务，最多累计 8 份提取文本批量写入 FTS。移除逐文件 15 ms 固定等待和逐文件进程启动；索引追平后只检查数据库修订号，避免不断重查整个候选集。暂停、关闭或重建正文索引后，已解析但未提交的旧结果会重新验证并被丢弃。

### 用户可选性能档位

位置：扫描状态 → **详情 → 扫描性能**。设置保存到本地数据库，扫描线程设置在下一批扫描生效，正文线程在任务批次边界调整。

| 档位 | 目录扫描线程 | 正文解析线程 |
|---|---:|---:|
| 自动 | 可用逻辑线程数，最多 4 | 可用逻辑线程数，最多 2 |
| 低占用 | 1 | 1 |
| 均衡 | 4 | 2 |
| 高性能 | 可用逻辑线程数，4–16 | 可用逻辑线程数，2–4 |

高并发不保证机械盘或网络盘更快，因此默认使用保守的自动档位。状态栏折叠时仍只保留一行；统计目录、扫描、整理索引和终态分开显示，不再用 99% 表示未完成错误。

## 验证

- Rust：83 项测试通过（68 单元、15 集成），包括取消/暂停、文件操作后重读、嵌套范围、局部扫描不改写其他子树、文件/目录替换、符号链接祖先拒绝、正文批处理提交前重验证及档位持久化。
- 前端：15 项进度状态测试、TypeScript/Vite 构建通过。浏览器实际操作检查了档位切换、详情鼠标/键盘开合、各扫描阶段、900/1,280 像素宽度和深色主题，未发现控制台或页面错误。浏览器使用模拟 API 状态；数据库行为由 Rust 测试覆盖。
- 常驻解析进程：同一真实子进程连续解析 80 份合成 PDF/DOCX/XLSX/PPTX，全部检出 `quartzneedle`，XLSX 数值 `12345` 正确。正文吞吐测速另走完整任务领取、进程回收和 FTS 查询路径。
- macOS workspace Rust 检查与 Windows x86_64 核心及测试代码交叉编译通过。另有 Windows 专用跨缓冲区测试，覆盖 1,001 个文件名/身份（含中文、硬链接）；该测试需 Windows CI/本机执行，交叉编译不等于运行通过。

## 对照测速

数据与方法见 [原始测速结果](benchmarks/performance-implementation-20260915.json)。使用同一基准程序、Release 构建、独立临时数据库和合成文件，关闭实时监听；每场景两轮，第二轮反转优化前后顺序。元数据场景每轮含首次建库与两次无变化刷新。计时含请求等待和状态轮询；每次检查最终文件总数，正文场景还检查完整检索命中数。

优化前基线是本次性能改动前的临时源码快照，已经包含之前的进度修复，并非未经修改的 v0.1.9 发布包。所有数值为 macOS 本地暖缓存样本，不能推断 Windows 全盘、冷缓存、HDD 或网络盘收益。

| 场景及计时范围 | 优化前平均 | 优化后平均 |
|---|---:|---:|
| 256 个小 TXT：从添加目录到全部可全文检索 | 20.067 s | 0.797 s |
| 30,000 文件 / 2 目录：首次建库 | 1.207 s | 0.980 s |
| 30,000 文件 / 2 目录：无变化刷新 | 0.734 s | 0.747 s |
| 30,000 文件 / 101 目录：首次建库 | 0.993 s | 1.042 s |
| 30,000 文件 / 101 目录：无变化刷新 | 0.632 s | 0.612 s |
| 30,000 文件 / 10,001 目录：首次建库 | 2.675 s | 2.635 s |
| 30,000 文件 / 10,001 目录：无变化刷新 | 1.676 s | 1.661 s |

正文小 TXT 场景约快 25 倍，主要减少了进程启动与固定等待，不代表复杂 Office/PDF 也有同样倍率。普通全量扫描没有一致的显著改善：平铺首次扫描更快，部分其他场景持平或略慢；两轮样本不足以断言总体收益。目录局部核对的收益是减少工作范围，已由针对性测试确认，此表没有给出其运行时倍率。

复现单个优化后样本（使用临时文件，不访问用户资料）：

```sh
node scripts/cargo.mjs build --release -p filem-core --example performance_benchmark
FILEM_SCAN_PROFILE=1 FILEM_BENCH_CONTENT=1 target/release/examples/performance_benchmark
FILEM_SCAN_PROFILE=1 FILEM_BENCH_COUNT=30000 FILEM_BENCH_DIRS=10000 target/release/examples/performance_benchmark
```

合成数据创建不计入扫描时间。正文结果验证 256 条全文命中；各元数据样本验证 30,000 个文件且无未完成范围。
